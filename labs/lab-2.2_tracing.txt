ТЕОРИЯ ЗА 5 МИНУТ
  Трейс — дерево спанов одного запроса. Спан — операция с началом, концом и атрибутами: в
  Istio каждый прокси создаёт спан на входящий и на исходящий вызов. Спаны связываются
  заголовками traceparent и tracestate (для Zipkin-совместимых бэкендов — B3), и приложение
  обязано их пробрасывать. В bookinfo это уже сделано, поэтому дерево получается связным.

  Трейсинг в Istio 1.25 настраивается двумя объектами. extensionProvider в MeshConfig
  описывает, куда и по какому протоколу прокси отправляют спаны. CR Telemetry в istio-system
  включает трейсинг во всём mesh и задаёт sampling: без него провайдер описан, но спаны не
  уходят. Default sampling равен 1%, поэтому на учебном стенде ставим 100%.

  Для Jaeger из демо-аддона есть два пути: провайдер opentelemetry на jaeger-collector:4317
  (так в документации 1.25 для Jaeger) и провайдер zipkin на сервис zipkin:9411 (сам аддон
  публикует его, потому что Jaeger принимает Zipkin API). Идём вторым путём: короче, а
  результат в Jaeger UI одинаковый.

  Главное для диагностики: трейс показывает, на каком ребре (кто -> кто) ушло время и где
  вернулась ошибка, но не говорит «почему». Второй шаг — конфигурация (VirtualService,
  DestinationRule, endpoints) и метрики ребра. 503 в mesh'е — ответ Envoy, а не приложения.

ШАГ 1. Убеждаемся, что трейсов пока нет

    k1 get telemetry -n istio-system
  ЗАЧЕМ: зафиксировать состояние до настройки: провайдера нет, спаны не уходят.

ШАГ 2. Описываем провайдера в MeshConfig

    helm upgrade istiod istio/istiod -n istio-system --version 1.25.2 --reuse-values \
      --set meshConfig.enableTracing=true \
      --set meshConfig.extensionProviders[0].name=jaeger \
      --set meshConfig.extensionProviders[0].zipkin.service=zipkin.istio-system.svc.cluster.local \
      --set meshConfig.extensionProviders[0].zipkin.port=9411 --wait
  ЗАЧЕМ: провайдер — адрес и протокол, по которому прокси отдают спаны. Остальное как в 2.1:
  меняем установку control plane, --reuse-values сохраняет access-логи, --version держит
  chart 1.25.2. Имя jaeger произвольно, тип zipkin — потому что Jaeger принимает Zipkin API
  на сервисе zipkin:9411.
  ВЫ УВИДИТЕ: Release «istiod» has been upgraded, STATUS: deployed.
  ПРОВЕРИТЬ НА СТЕНДЕ: что спаны действительно доходят до Jaeger через zipkin:9411, а не
  только появляются в конфигурации прокси.

  Проверяем конфигурацию:
    k1 get configmap -n istio-system -o yaml | grep -A6 extensionProviders
  ВЫ УВИДИТЕ: extensionProviders, ниже name: jaeger и zipkin с service и port.

ШАГ 3. Включаем трейсинг и sampling

    k1 apply -f - <<'EOF'
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: mesh-default
  namespace: istio-system
spec:
  tracing:
    - providers:
        - name: jaeger
      randomSamplingPercentage: 100.0
EOF
  ЗАЧЕМ: провайдер описывает бэкенд, а включает трейсинг объект Telemetry. Он создан в
  корневом namespace istio-system, поэтому действует на весь mesh. sampling поднимаем с 1%
  до 100%: на учебном стенде трафика мало, при 1% мы почти ничего не увидим.
  ВЫ УВИДИТЕ: telemetry.telemetry.istio.io/mesh-default created.

    k1 get telemetry -n istio-system
  ВЫ УВИДИТЕ: mesh-default в списке.

ШАГ 7. ИНЦИДЕНТ 2. Задержка: первый VirtualService

  Уберём разброс по версиям reviews: у v1 нет вызова ratings, у v3 таймаут на ratings 2,5 с,
  у v2 — 10 с. Чтобы замер и трейс были одинаковыми, оставим одну версию.
    k1 scale deployment -n bookinfo reviews-v1 --replicas=0
    k1 scale deployment -n bookinfo reviews-v3 --replicas=0
  ЗАЧЕМ: сделать инцидент воспроизводимым, а не зависящим от того, какой под ответил.
  ВЫ УВИДИТЕ: два "scaled".

  Создаём VirtualService с задержкой:
    k1 apply -f - <<'EOF'
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: ratings-delay
  namespace: bookinfo
spec:
  hosts:
    - ratings
  http:
    - fault:
        delay:
          percentage:
            value: 100
          fixedDelay: 7s
      route:
        - destination:
            host: ratings
EOF
  ЗАЧЕМ: VirtualService — первый объект маршрутизации в курсе, подробно разбираем в 3.1.
  Здесь нужен один блок: fault.delay вставляет задержку в прокси на клиентской стороне, до
  того как запрос уйдёт в ratings. Короткое имя ratings резолвится по namespace самого
  VirtualService, то есть ratings.bookinfo.svc.cluster.local.
  ВЫ УВИДИТЕ: virtualservice.networking.istio.io/ratings-delay created.

ШАГ 8. ИНЦИДЕНТ 2. Измеряем и ищем ребро задержки

    for i in 1 2 3; do
      curl -s -o /dev/null -w "%{time_total}\n" "http://$INGRESS_HOST/productpage"
    done
  ЗАЧЕМ: -w "%{time_total}" печатает полное время запроса в секундах с микросекундами — так
  меряют latency в скриптах, без разбора вывода time и без шума прогрева соединений.
  ВЫ УВИДИТЕ: три значения около 6,0 секунды, хотя задержка в конфигурации 7 секунд. Дело не
  в стенде: productpage ждёт reviews не дольше 3 секунд и делает один повтор, 3 + 3 = 6
  секунд, после чего показывает ошибку в блоке отзывов. Это известная особенность bookinfo.

    curl -s "http://$INGRESS_HOST/productpage" | grep -c "Error fetching"
  ВЫ УВИДИТЕ: 1 — блок отзывов сломан, хотя reviews v2 жив и отвечает.

  В Jaeger отсортируйте трейсы по Duration (самый долгий сверху).
  ВЫ УВИДИТЕ: трейс около 6 секунд. В нём спан на ребре reviews -> ratings длительностью около
  7 секунд — та самая задержка; два спана productpage -> reviews примерно по 3 секунды с
  ошибкой (две попытки, обе оборвал таймаут приложения); серверный спан ratings — единицы
  миллисекунд. Вывод: время уходит на ребре reviews -> ratings, в ratings задержки нет.
