ТЕОРИЯ ЗА 5 МИНУТ
  Кто выпускает сертификаты. По умолчанию CA встроен в istiod: он создаёт self-signed root
  и подписывает SVID рабочих нагрузок. Такой CA доверяет только Kubernetes — namespace плюс
  ServiceAccount. За пределами кластера (ВМ, другой кластер, bare metal) подтвердить identity нечем.

  SPIFFE — стандарт identity для распределённых систем. Identity задаётся URI
  spiffe://<trust domain>/ns/<namespace>/sa/<serviceAccount>. SPIRE — реализация стандарта:
  SPIRE Server хранит CA и регистрации, SPIRE Agent работает на каждом узле и подтверждает,
  кто именно просит сертификат (node и workload attestation). Выданный сертификат — SVID.

  Как SPIRE связан с Envoy. Istio умеет обнаружить UNIX-сокет SDS на стандартном пути
  /var/run/secrets/workload-spiffe-uds/socket и брать identity оттуда вместо istiod. Сокет
  монтируется в под через SPIFFE CSI driver (том csi.spiffe.io). Без CSI-тома и без шаблона
  inject.istio.io/templates: "sidecar,spire" под получит обычный сертификат istiod.

  Регистрации. SPIRE выдаёт identity только зарегистрированным workload'ам. ClusterSPIFFEID —
  CRD SPIRE Controller Manager: описывает selector (namespace, ServiceAccount, метка пода) и
  шаблон SPIFFE ID. Istio требует формат spiffe://<trustDomain>/ns/<ns>/sa/<sa>, поэтому шаблон
  всегда одинаковый. Trust domain в SPIRE и в Istio обязан совпадать, иначе mTLS не заработает:
  поэтому IstioOperator задаёт meshConfig.trustDomain: example.org.

ШАГ 3. Описываем регистрации через ClusterSPIFFEID

    k1 apply -f - <<'EOF'
    apiVersion: spire.spiffe.io/v1alpha1
    kind: ClusterSPIFFEID
    metadata:
      name: istio-ingressgateway-reg
    spec:
      spiffeIDTemplate: >-
        spiffe://{{ .TrustDomain }}/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}
      workloadSelectorTemplates:
        - "k8s:ns:istio-system"
        - "k8s:sa:istio-ingressgateway-service-account"
    EOF

    k1 apply -f - <<'EOF'
    apiVersion: spire.spiffe.io/v1alpha1
    kind: ClusterSPIFFEID
    metadata:
      name: istio-sidecar-reg
    spec:
      spiffeIDTemplate: >-
        spiffe://{{ .TrustDomain }}/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}
      podSelector:
        matchLabels:
          spiffe.io/spire-managed-identity: "true"
      workloadSelectorTemplates:
        - "k8s:ns:bookinfo"
    EOF
  ЗАЧЕМ: SPIRE выдаёт SVID только зарегистрированным. Controller manager смотрит на
  ClusterSPIFFEID и создаёт entry, когда появляется подходящий под.
  Первый объект — для ingress gateway в istio-system, второй — для sidecar в bookinfo.
  ВЫ УВИДИТЕ: clusterspiffeid.spire.spiffe.io/istio-ingressgateway-reg created
  и clusterspiffeid.spire.spiffe.io/istio-sidecar-reg created.

ШАГ 4. Готовим IstioOperator с CSI-монтированием

    cat > ~/istio-spire.yaml <<'EOF'
    apiVersion: install.istio.io/v1alpha1
    kind: IstioOperator
    metadata:
      namespace: istio-system
    spec:
      profile: default
      meshConfig:
        trustDomain: example.org
      values:
        sidecarInjectorWebhook:
          templates:
            spire: |
              labels:
                spiffe.io/spire-managed-identity: "true"
              spec:
                containers:
                  - name: istio-proxy
                    volumeMounts:
                      - name: spire
                        mountPath: /run/secrets/workload-spiffe-uds
                        readOnly: true
                volumes:
                  - name: spire
                    csi:
                      driver: "csi.spiffe.io"
                      readOnly: true
      components:
        ingressGateways:
          - name: istio-ingressgateway
            enabled: true
            label:
              istio: ingressgateway
            k8s:
              overlays:
              - apiVersion: apps/v1
                kind: Deployment
                name: istio-ingressgateway
                patches:
                - path: spec.template.spec.volumes.[name:spire]
                  value:
                    name: spire
                    csi:
                      driver: "csi.spiffe.io"
                      readOnly: true
                - path: spec.template.spec.containers.[name:istio-proxy].volumeMounts.[name:spire]
                  value:
                    name: spire
                    mountPath: "/run/secrets/workload-spiffe-uds"
                    readOnly: true
    EOF
  ЗАЧЕМ: три изменения в установке. meshConfig.trustDomain — общая доверенная область.
  Шаблон spire — то, что вебхук инъекции добавит поду с аннотацией inject.istio.io/templates:
  метку для ClusterSPIFFEID, CSI-том и его монтирование в istio-proxy. Патчи в components
  делают то же самое для gateway: он не инжектируется, а рендерится чартом.
  ВЫ УВИДИТЕ: файл ~/istio-spire.yaml создан; вывода у команды нет.
  ПРОВЕРИТЬ НА СТЕНДЕ: в Istio 1.25.2 native sidecars по умолчанию выключены, и на
  проверенном стенде (Kubernetes 1.36) istio-proxy остаётся в spec.containers — шаблон
  использует containers. Если в вашей сборке native sidecars включены, проверьте
  фактическое место sidecar и поменяйте шаблон:
    k1 get pod -n bookinfo <pod> -o jsonpath='{.spec.initContainers[*].name}'
  Если istio-proxy в initContainers — в шаблоне spire нужны initContainers, иначе под
  не создастся (вебхук добавит второй init-контейнер без образа).

ШАГ 8. Проверяем, что SVID выпустил SPIRE

    SPIRE_SERVER_POD=$(k1 get pod -n spire-server \
      -l statefulset.kubernetes.io/pod-name=spire-server-0 \
      -o jsonpath='{.items[0].metadata.name}')
    k1 exec -n spire-server "$SPIRE_SERVER_POD" -c spire-server -- \
      /opt/spire/bin/spire-server entry show
  ЗАЧЕМ: посмотреть регистрации, которые controller manager создал автоматически.
  ВЫ УВИДИТЕ: записи с SPIFFE ID от example.org — среди них gateway
  (spiffe://example.org/ns/istio-system/sa/istio-ingressgateway-service-account), под curl
  и остальные поды bookinfo, которым ClusterSPIFFEID выдал identity (обычно ~15 записей).

    CURL_POD=$(k1 get pod -n bookinfo -l app=curl -o jsonpath='{.items[0].metadata.name}')
    istioctl proxy-config secret "$CURL_POD" -n bookinfo -o json > svid.json
    jq -r '.dynamicActiveSecrets[0].secret.tlsCertificate.certificateChain.inlineBytes' \
      svid.json | base64 -d > chain.pem
  ЗАЧЕМ: вытащить цепочку сертификатов, которой Envoy реально пользуется. Эту команду
  даёт документация 1.25; имя пода берём через POD=, а не через -l у exec.
  ВЫ УВИДИТЕ: два файла: svid.json и chain.pem. Ошибок быть не должно.

    openssl x509 -in chain.pem -noout -issuer -ext subjectAltName
  ЗАЧЕМ: issuer показывает CA, а SAN — SPIFFE identity. У SPIRE 1.15 subject
  рабочего сертификата пустой, поэтому проверять надо issuer и SAN, а не CN.
  ВЫ УВИДИТЕ: issuer=O=example.org (trust domain SPIRE) и
  URI:spiffe://example.org/ns/bookinfo/sa/curl. У сертификата от istiod
  issuer был бы O=cluster.local.
