ТЕОРИЯ ЗА 5 МИНУТ
  Встроенный CA. istiod сам создаёт self-signed root и подписывает сертификаты workloads.
  Для эксплуатации это плохо: root-ключ лежит в кластере, сменить CA без разрыва mTLS нельзя.
  Плагин CA. Если при старте istiod находит в /etc/cacerts четыре файла, он подписывает
  сертификаты ими: ca-cert.pem — сертификат промежуточного CA, ca-key.pem — его ключ,
  root-cert.pem — корневой сертификат, cert-chain.pem — ca-cert плюс root. Источник файлов —
  secret cacerts в istio-system; том необязательный, поэтому секрет можно создать позже
  и перезапустить istiod.

  Иерархия PKI. Root CA держат в защищённом месте (здесь — в Vault), кластеру выдают
  intermediate: при утечке его ключа отзывают intermediate, не меняя root. Vault PKI —
  хранилище, которое выпускает и подписывает сертификаты по API.

  Vault Agent Injector. Mutating webhook смотрит на аннотации пода и добавляет контейнеры
  vault-agent. Агент аутентифицируется в Vault по ServiceAccount (Kubernetes auth), получает
  токен по роли и рендерит секрет в файл /vault/secrets/<имя>. Приложение не знает ни адреса
  Vault, ни пароля — читает файл.

  StatefulSet и headless. Headless-сервис (clusterIP: None) даёт подам стабильные DNS-имена
  вида db-0.db.bookinfo.svc.cluster.local. TCP-сервис описывают в реестре Istio через
  ServiceEntry с protocol: TCP: иначе Envoy может принять поток за HTTP и сломать его.

ШАГ 1. Ставим Vault в dev-режиме

    helm repo add hashicorp https://helm.releases.hashicorp.com || true
    helm repo update
    # Если репозиторий отдаёт 403 (бывает в закрытых сетях), чарт ставится из GitHub:
    #   git clone --depth 1 https://github.com/hashicorp/vault-helm.git /tmp/vault-helm
    #   helm install vault /tmp/vault-helm -n vault --create-namespace --set server.dev.enabled=true
    helm install vault hashicorp/vault -n vault --create-namespace \
      --set server.dev.enabled=true --wait
  ЗАЧЕМ: dev-режим учебный: Vault сразу распакован, root token известен, PKI включается
  командами. Данные живут в памяти и исчезнут после рестарта пода.
  ВЫ УВИДИТЕ: NAME: vault, STATUS: deployed.

    k1 get pods -n vault
  ВЫ УВИДИТЕ: vault-0 1/1 и vault-agent-injector-xxxxx 1/1 — сервер и вебхук инъекции.
  В dev-режиме root token — root; передаём его в команды через env VAULT_TOKEN.

ШАГ 2. Включаем PKI и создаём root CA

    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root vault secrets enable pki
  ЗАЧЕМ: включить движок pki для выпуска сертификатов.
  ВЫ УВИДИТЕ: Success! Enabled the pki secrets engine at: pki/.

    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root \
      vault secrets tune -max-lease-ttl=87600h pki
    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root \
      vault write pki/root/generate/internal common_name=cluster.local ttl=87600h
  ЗАЧЕМ: создать self-signed root внутри Vault. Ключ root не покинет Vault: наружу отдадим
  только intermediate.
  ВЫ УВИДИТЕ: таблицу Key Value: certificate, issuing_ca, serial_number.

ШАГ 3. Выпускаем intermediate CA

    openssl genrsa -out ca-key.pem 4096
    openssl req -new -key ca-key.pem -out cluster-ca.csr \
      -subj "/O=Istio/CN=cluster.local Intermediate Authority"
  ЗАЧЕМ: ключ и CSR промежуточного CA генерируем у себя: приватный ключ нужен istiod,
  Vault только подпишет CSR.
  ВЫ УВИДИТЕ: два файла: ca-key.pem и cluster-ca.csr.

    CSR=$(cat cluster-ca.csr)
    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root vault write \
      -field=certificate pki/root/sign-intermediate csr="$CSR" ttl=43800h \
      common_name="cluster.local Intermediate Authority" > ca-cert.pem
  ЗАЧЕМ: подписать CSR корневым CA в Vault и сохранить сертификат intermediate локально.
  ВЫ УВИДИТЕ: файл ca-cert.pem; команда не печатает, сертификат уходит в файл.

    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root \
      vault read -field=certificate pki/cert/ca > root-cert.pem
  ВЫ УВИДИТЕ: файл root-cert.pem — корневой сертификат для цепочки доверия.

ШАГ 4. Собираем secret cacerts и перезапускаем istiod

    { cat ca-cert.pem; echo; cat root-cert.pem; } > cert-chain.pem
    openssl verify -CAfile root-cert.pem ca-cert.pem
  ЗАЧЕМ: cert-chain.pem — ровно ca-cert плюс root, как в документации Istio
  «Plug in CA Certificates». Проверка подтверждает, что цепочка сходится.
  ВЫ УВИДИТЕ: ca-cert.pem: OK.

    k1 create secret generic cacerts -n istio-system \
      --from-file=ca-cert.pem --from-file=ca-key.pem \
      --from-file=root-cert.pem --from-file=cert-chain.pem
  ЗАЧЕМ: имена файлов в секрете фиксированы: istiod читает именно их из /etc/cacerts.
  ВЫ УВИДИТЕ: secret/cacerts created.

    ISTIOD=$(k1 get deploy -n istio-system -l app=istiod -o jsonpath='{.items[0].metadata.name}')
    k1 rollout restart deployment "$ISTIOD" -n istio-system
    k1 rollout status deployment "$ISTIOD" -n istio-system --timeout=180s
  ЗАЧЕМ: istiod читает CA только при старте, поэтому новый секрет применяется рестартом.
  ВЫ УВИДИТЕ: deployment "istiod-1-25" successfully rolled out.

ШАГ 5. Проверяем, что сертификаты выпускает CA из Vault

    k1 rollout restart deployment -n bookinfo
    k1 rollout status deployment/productpage-v1 -n bookinfo --timeout=180s
  ЗАЧЕМ: перезапускаем всё приложение: старые сертификаты подписаны прежним CA и по новой
  цепочке доверия не проходят.
  ВЫ УВИДИТЕ: deployment "productpage-v1" successfully rolled out.

    PRODUCTPAGE_POD=$(k1 get pod -n bookinfo -l app=productpage \
      -o jsonpath='{.items[0].metadata.name}')
    istioctl proxy-config secret "$PRODUCTPAGE_POD" -n bookinfo -o json > pp.json
    jq -r '.dynamicActiveSecrets[0].secret.tlsCertificate.certificateChain.inlineBytes' \
      pp.json | base64 -d > pp-chain.pem
  ЗАЧЕМ: достать цепочку сертификатов, которой Envoy реально пользуется.
  ВЫ УВИДИТЕ: файлы pp.json и pp-chain.pem без ошибок.

    openssl x509 -in pp-chain.pem -noout -issuer | grep Intermediate
  ЗАЧЕМ: issuer рабочего сертификата — тот, кто его подписал. Это и есть проверка нового CA.
  ВЫ УВИДИТЕ: issuer=CN = cluster.local Intermediate Authority — цепочка идёт от Vault.

ШАГ 6. Настраиваем Vault Agent Injector

    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root vault auth enable kubernetes
    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root vault write auth/kubernetes/config \
      kubernetes_host="https://kubernetes.default.svc"
  ЗАЧЕМ: Vault должен проверять токены ServiceAccount через API Kubernetes.
  ВЫ УВИДИТЕ: Success! Enabled kubernetes auth method at: kubernetes/.

    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root vault kv put secret/db \
      username=bookinfo password=S3cretPass
  ЗАЧЕМ: пароль хранится только в Vault, в манифесте пода его не будет.
  ВЫ УВИДИТЕ: Key Value в secret/data/db: username и password.

    printf 'path "secret/data/db" {\n  capabilities = ["read"]\n}\n' > db-policy.hcl
    k1 exec -i -n vault vault-0 -- env VAULT_TOKEN=root vault policy write db - < db-policy.hcl
  ЗАЧЕМ: policy даёт минимальные права: только чтение одного секрета.
  ВЫ УВИДИТЕ: Success! Uploaded policy: db.

    k1 exec -n vault vault-0 -- env VAULT_TOKEN=root vault write auth/kubernetes/role/db \
      bound_service_account_names=db bound_service_account_namespaces=bookinfo \
      policies=db ttl=1h
  ЗАЧЕМ: роль связывает ServiceAccount db в namespace bookinfo с policy db: чужой SA токен
  не получит.
  ВЫ УВИДИТЕ: Success! Data written to: auth/kubernetes/role/db.

ШАГ 7. Разворачиваем StatefulSet с headless-сервисом и ServiceEntry

    k1 apply -n bookinfo -f - <<'EOF'
apiVersion: v1
kind: ServiceAccount
metadata:
  name: db
---
apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None
  selector:
    app: db
  ports:
    - name: tcp-db
      port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db
  replicas: 2
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "db"
        vault.hashicorp.com/agent-inject-secret-config: "secret/data/db"
        vault.hashicorp.com/service: "http://vault.vault:8200"
        # init-контейнер vault-agent стартует раньше istio-proxy; без исключения
        # порта 8200 его трафик уходит в ещё не поднятый Envoy и получает connection refused
        traffic.sidecar.istio.io/excludeOutboundPorts: "8200"
    spec:
      serviceAccountName: db
      containers:
        - name: db
          image: busybox:1.36
          command: ["sh", "-c", "while true; do echo ok | nc -l -p 5432; done"]
---
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata:
  name: db-headless
spec:
  hosts:
    - db.bookinfo.svc.cluster.local
  ports:
    - number: 5432
      name: tcp-db
      protocol: TCP
  resolution: DNS
  endpoints:
    - address: db-0.db.bookinfo.svc.cluster.local
    - address: db-1.db.bookinfo.svc.cluster.local
EOF
  ЗАЧЕМ: четыре объекта. ServiceAccount db — для Vault auth и identity в mesh. Headless-сервис
  даёт подам DNS-имена. StatefulSet с аннотациями vault.hashicorp.com/ — приложение с секретом
  из Vault. ServiceEntry описывает TCP-сервис в реестре Istio: protocol TCP не даёт Envoy
  трактовать поток как HTTP.
  ВЫ УВИДИТЕ: serviceaccount/db created, service/db created, statefulset.apps/db created,
  serviceentry.networking.istio.io/db-headless created.
  ПРОВЕРИТЬ НА СТЕНДЕ: в 1.25 headless-сервис уже есть в реестре Istio, и ServiceEntry
  с тем же host трактуется как декоратор (NOTE 2 в документации ServiceEntry). Практический
  эффект проверяем в шаге 8; если listener на 5432 не появился — см. третий блок проблем.

ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК

ПРОБЛЕМА: istiod после рестарта не поднимается, в логах ошибки чтения CA из /etc/cacerts
ПРИЧИНА: в secret cacerts не те имена файлов или битый ключ: istiod ждёт ровно ca-cert.pem,
ca-key.pem, root-cert.pem, cert-chain.pem.
ЧТО ДЕЛАТЬ:
  1. Проверить ключи секрета: k1 get secret cacerts -n istio-system -o jsonpath='{.data}'.
  2. Сверить пару сертификат-ключ: openssl x509 -in ca-cert.pem -noout -modulus и
     openssl rsa -in ca-key.pem -noout -modulus — значения должны совпасть.
  3. Посмотреть лог: k1 logs -n istio-system "$ISTIOD" -c discovery | grep -i cacerts.

ПРОБЛЕМА: под db висит в ContainerCreating или Init, в READY не 3/3
ПРИЧИНА: Vault Agent не получил токен: не совпали ServiceAccount, namespace или роль.
ЧТО ДЕЛАТЬ:
  1. Посмотреть init-контейнер: k1 logs -n bookinfo db-0 -c vault-agent-init.
  2. Сверить привязку: k1 exec -n vault vault-0 -- env VAULT_TOKEN=root vault read
     auth/kubernetes/role/db.
  3. Проверить адрес в аннотации: vault.hashicorp.com/service должен быть http://vault.vault:8200.

ПРОБЛЕМА: listener на порту 5432 не появился, istioctl analyze предупреждает о дубликате host
ПРИЧИНА: headless-сервис уже есть в реестре Istio, и ServiceEntry с тем же host — декоратор:
порты и endpoints из него могут не примениться.
ЧТО ДЕЛАТЬ:
  1. Проверить конфигурацию: istioctl proxy-config listeners "$DB0" -n bookinfo.
  2. Если порта нет, переименовать host в ServiceEntry (например, db-mesh) и добавить
     workloadSelector по метке app: db либо оставить штатную поддержку headless-сервисов.
