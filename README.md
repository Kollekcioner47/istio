## О курсе

Курс для эксплуатационных инженеров: тех, кто уже работает с Linux и Kubernetes, но Istio
видит впервые. Нужно уметь читать YAML, работать с `kubectl` и понимать, что такое под,
сервис и namespace. Знание Envoy, xDS и SPIFFE не предполагается — всё разбирается с нуля.

Главный принцип: **каждый шаг проверяется командой**. У каждого действия есть `ЗАЧЕМ`,
у каждого результата — `ВЫ УВИДЕТЕ`, а если что-то не так, рядом лежит разбор
«ПРОБЛЕМА / ПРИЧИНА / ЧТО ДЕЛАТЬ». Это тот же формат, что в курсах автора по Docker
и Kubernetes.

**Что в курсе есть:**

- **21 лабораторная работа** — по одной-три на модуль, на 90–120 минут, с целями, предусловиями,
  проверкой результата, уборкой и мостиком к следующей.
- **Два настоящих кластера** — `cluster-1` (5 узлов) и `cluster-2` (2 узла), плюс внешняя ВМ
  для Mesh Expansion. Multicluster и ambient проверяются на живом стенде.
- **Инциденты, а не только примеры.** 8.1 — четыре управляемых инцидента с полной диагностикой
  и пост-мортемом, 8.2 — три слепых мини-инцидента, итоговый кейс — 3–4 поломки без подсказок.
- **Разборы, которые не ломают стенд.** Всё, что меняет control plane, заканчивается
  `scripts/reset-istio.sh`; состояние стенда описано в каждой работе.
- **Теория с командами и схемами** — 12–16 слайдов на модуль, к каждой работе есть слайд
  с командой ровно в том виде, в каком она нужна.

Сквозное приложение — **bookinfo**: маршрутизация, mTLS, трейсы, инциденты. Для gateway-тем
добавляется `httpbin`, чтобы CORS, JWT и rate limiting не смешивались с bookinfo.

## Что понадобится для занятий

Стенд собирается по [`setup-guide.md`](setup-guide.md) — это единственный шаг, требующий
отдельной подготовки. Курс рассчитан на изолированную лабораторию: команды меняют mesh,
удаляют namespace и намеренно ломают кластер.

| | |
|---|---|
| **Виртуальные машины** | 9 (VirtualBox 7.1+): admin, 3 control plane + 2 worker кластера-1, control plane + worker кластера-2, внешняя ВМ |
| **Кластеры** | 2 кластера Kubernetes 1.32+ (проверено на 1.36.2), kubespray, Calico |
| **ОС** | Ubuntu 26.04 LTS на всех ВМ |
| **Ресурсы** | около 44 GB памяти и 120+ GB диска на хосте |
| **Сеть** | стенд 10.0.2.0/24 + управление 192.168.56.0/24 |
| **Внешние адреса** | MetalLB, пул 192.168.56.240–250 (если Host-Only недоступен — 10.0.2.240–250, setup-guide §10a) |
| **Учётная запись** | `engineer` с sudo, пароль `Console47` (стенд изолирован) |
| **Инструменты на admin** | kubectl 1.32+, Helm 3.21.x, istioctl 1.25.2, ArgoCD CLI 2.14.x — setup-guide §7; проверка/установка istioctl — работа 1.1, шаг 0 |

Если `admin` чистый (есть только kubeconfig), инструменты ставятся одной командой:
`bash scripts/bootstrap-admin.sh` — нужны интернет и `sudo`. На стенде, собранном по
`setup-guide`, они уже стоят.

Урезанный стенд (6 машин, ~22 GB) описан в [`architecture.md`](architecture.md) §1.5.

**Можно ли проходить на своём кластере?** Работы 1.1–5.3 — да, если есть Istio 1.25.2,
MetalLB и metrics-server. Для 6.1 нужны два кластера, для 6.2 — внешняя ВМ, для 7.1 — ядро
и CNI, поддерживающие ambient. Команды курса написаны под стенд из `architecture.md`.
Если `istioctl` ещё нет — установите его по шагу 0 работы 1.1: дистрибутив заодно даёт
`samples/` и `manifests/`, которые нужны в следующих работах.

### Как устроена каждая лабораторная работа

Формат одинаковый во всех 21 работах (13 обязательных разделов):

**Шапка и цели.** Модуль, длительность, сложность, тип, состояние стенда до и после, ссылка
на следующую работу, 2–4 измеримые цели.

**«ЧТО ПОНАДОБИТСЯ» и «ПРОВЕРКА СТЕНДА».** Чек-лист и команды, которыми студент сам
убеждается, что стенд в нужном состоянии.

**«ТЕОРИЯ ЗА 5 МИНУТ».** Один экран: что за механизм, зачем нужен, из каких объектов состоит.
Без команд — команды ниже.

**Шаги.** Команда, `ЗАЧЕМ` и `ВЫ УВИДЕТЕ` — конкретная строка или поле в выводе.

**«ПРОВЕРКА РЕЗУЛЬТАТА» и «ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК».** Одна-две команды с ожидаемым
результатом и минимум три блока «ПРОБЛЕМА / ПРИЧИНА / ЧТО ДЕЛАТЬ» с точным текстом ошибки.

**Дополнительное задание, вопросы, «УБОРКА», «ЧТО ДАЛЬШЕ».** Одно задание на 10–20 минут,
4–6 вопросов, что удалить и какое состояние осталось, одна фраза-мостик.

## Как начать

1. **Соберите стенд** по [`setup-guide.md`](setup-guide.md) — 3–4 часа. Результат: 9 ВМ,
   два кластера, MetalLB, metrics-server и инструменты на `admin`.
2. **Проверьте готовность:**

   ```bash
   source ~/istio-course/scripts/env.sh
   k1 get nodes && k2 get nodes && k1 top nodes
   ```

   Ожидаемо: 5 и 2 узла `Ready`, таблица метрик, `istioctl` 1.25.2 в PATH. Полный чек-лист —
   `setup-guide.md` §17.

3. **Сделайте снапшот** `baseline` или `k8s-ready`: `scripts/snapshot.ps1 -Action take -Name k8s-ready`.
4. **Проходите работы по порядку.** Каждая опирается на предыдущие: ревизии (1.2) — поверх
   установки (1.1), аддоны (2.1) дают метрики, без которых не разобрать деградацию (2.2),
   без трафика (3.x) нет смысла в политиках (4.x). Порядок — `architecture.md` §3.3.
5. **Перед работами с инцидентами** проверьте, что стенд в состоянии `k8s-ready`:
   `k1 get pods -n bookinfo` — все поды `2/2 Running`.

## Соглашения в материалах

Версии зафиксированы и проверены на стенде: команда, работавшая на другой версии, может
вести себя иначе.

| Компонент | Версия |
|---|---|
| Istio | 1.25.2 (дистрибутив `~/istio-1.25.2`) |
| Kubernetes | 1.32+ (проверено на 1.36.2), kubespray, Calico |
| Helm | 3.21+ (проверено 3.21.3) |
| kubectl | 1.32+ (проверено 1.36.2) |
| Ubuntu | 26.04 LTS |
| MetalLB | 0.14+ (пул 192.168.56.240–250; fallback 10.0.2.240–250, §10a) |
| metrics-server | 0.7+ |
| ArgoCD | server 2.14, CLI 2.14.x (пин) |
| SPIRE | 1.11+ |
| Kiali, Prometheus, Grafana, Jaeger | из `~/istio-1.25.2/samples/addons` |

**Окружение.** Всё окружение — в `scripts/env.sh`: версия Istio, kubeconfig обоих кластеров,
функции `k1`/`k2`, `istioctl` в PATH, `INGRESS_HOST`. Файл подключается в `~/.bashrc`;
в работах окружение не переопределяется.

**Кластеры.** `k1` — cluster-1, `k2` — cluster-2. Работы, которым нужен только cluster-1,
пишут `k1` явно: студент видит, какой кластер трогает.

**Адрес приложения.** Только `$INGRESS_HOST` — внешний адрес из MetalLB. Обращаться
к `istio-ingressgateway.istio-system` с `admin` нельзя: это DNS-имя внутри кластера,
с машины управления оно не резолвится.

**Namespace.** `bookinfo` — во всех работах; `httpbin` — для gateway-тем, создаётся и
удаляется в своей работе. Namespace `default` не используется.

**`kubectl exec`.** Только по имени пода:
`POD=$(k1 get pod -n bookinfo -l app=ratings -o jsonpath='{.items[0].metadata.name}')`.
Флага `-l` у `kubectl exec` не существует.

**Состояние стенда.** Три опорные точки: `baseline` (без Istio), `k8s-ready` (Istio baseline,
bookinfo в mesh) и `incident` (намеренно сломанный стенд). Возврат — `reset-istio.sh`,
`reset-apps.sh`, снапшоты; таблица — `architecture.md` §6.

## Чего в курсе нет — сознательно

| Не разбирается | Почему |
|---|---|
| Топология primary-primary | удваивает объём 6.1 без новой оси; даётся обзором в теории модуля 6 |
| Управляемые mesh (Anthos, OpenShift Service Mesh) | другой продукт и другая эксплуатация |
| Terraform и Ansible для самого Istio | курс про mesh, а не про IaC; GitOps закрыт в 9.1 |
| Свои Envoy-фильтры на C++/WASM | это разработка, а не эксплуатация; `EnvoyFilter` и Lua разбираются в 5.2 |
| Windows-контейнеры и Windows-узлы | стенд на Linux; mesh на Windows — отдельная тема |
| Сертификация Istio (ICA) | курс практический; вопросы сертификации не разбираются |

## Обратная связь

Если что-то не работает на вашей версии Istio или стенд собрался не так, присылайте:
вывод `istioctl version`, `kubectl version`, что делали и полный текст ошибки — с текстом
ошибки исправление попадёт в курс быстрее. Перед письмом пройдите чек-лист готовности стенда
(`setup-guide.md` §17): половина вопросов снимается им.
